# Project rules

Project: UBSI documentation hub, EPITA SIGL enterprise-architecture course project modeling the information system of AirSIGL (fictional airline). Referentials live as CSV in `data/`, a MkDocs Material site is generated from them.

## Commands

- Install: `pip install -r requirements.txt`
- Validate data: `python scripts/validate.py`
- Build site: `mkdocs build --strict`
- Preview: `mkdocs serve`

## Rules

- All code, comments, commits and repo docs (README, CLAUDE.md, ADRs, specs) in English. Site content in `docs/` (pages read by the team) and data values in `data/` are in French.
- `data/` is the only place data lives. Never copy data into `docs/` or `site/`; pages for referentials are generated by `site/hooks/data_pages.py`. `site/` is presentation only.
- Any new column or dataset is declared in `data/schema.yaml` first.
- The repo and site are public: never add personal data (emails, Forge logins, student IDs) to `data/`.
- Code never goes directly to the default branch (or the branch named here): use a `feat/…` or `fix/…` branch and a pull request with passing checks. Docs (`docs/**`, this file) may be committed straight to it.
- Trivial change (typo, small obvious bug): no spec, just a `fix/…` branch and a pull request.
- A request that is not a bug fix or a trivial change starts as `/spec new` (explore, then draft spec). No code until a spec is `ready`.
- Conventional Commits, with the spec reference when there is one: `feat(auth): lock account after 5 failures (SPEC-012)`.
- Run the commands above before each commit that touches code. Never weaken a test to make it pass unless the spec changed.
- If a spec, an ADR and the code disagree, stop and report it. Do not resolve it silently.
- Specs and ADRs live in `docs/` and follow the `/spec` skill (formats and workflow).
- If the session-start board lists drafts or proposed ADRs, mention them in one line in your first reply.
